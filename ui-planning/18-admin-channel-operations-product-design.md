# Partokens 管理员渠道运营台产品设计

状态：方案已确认，渠道模型运营增强已实现，待真实 new-api 集成验收
日期：2026-08-25（Asia/Shanghai）
范围：Root 渠道管理、分组路由、持续监控和非原子变更续跑

## 1. 产品结论

### 1.1 同一上游的多密钥交互结论

当多个密钥共用一个上游地址时，数据和路由层保持分开：渠道类型、密钥指纹、成本倍率、模型清单、健康状态和逻辑 ID 都属于独立的逻辑渠道，不能因为地址相同而合并。管理界面按规范化上游地址做视觉归组，组内展开每个密钥变体；这样可以减少重复地址带来的扫描成本，同时保留逐密钥复制、启停、测试、模型运营和路由绑定能力。

复制操作复制非敏感配置（名称、类型、地址、倍率、模型和备注），必须重新输入新密钥；新记录获得新的逻辑 ID 和密钥指纹，不会读取或回显源密钥。

新增一套 Partokens 自有的管理员渠道运营台，不复刻 new-api 官方渠道表格。管理员操作的是稳定的“逻辑渠道”和“分组路由”，系统负责把一次操作转换为一组 new-api 物理渠道变更。

首版建议包含四个直接可工作的页面：

1. **渠道**：按渠道类型、规范化 API 地址、API 密钥身份去重后的逻辑渠道目录。
2. **分组路由**：按请求尝试次数编排渠道池、权重与回退顺序。
3. **监控**：查看逻辑渠道、底层执行记录和分组路由的当前可用状态。
4. **变更记录**：预览、执行、续跑和核对一次涉及多条物理记录的操作。

不新增介绍型管理员首页。管理员进入后直接落在“渠道”页。

### 1.2 已确认的实现边界

```text
partokens-ui /{locale}/console/admin/*
                ↓ 同源 /admin-api/*
partokens-admin-api（FastAPI + httpx + stdlib sqlite3）
                ↓ 支持的 HTTP API
          单个、未修改的 new-api
```

- 新增独立兄弟项目 `partokens-admin-api`，不把后端运行时嵌入 `partokens-ui`。
- 服务只管理一个 new-api 实例，不直接访问其 PostgreSQL，也不修改 new-api。
- SQLite 保存逻辑渠道、路由修订、执行步骤和监控快照；首版只能运行一个服务实例。
- 每个请求都用当前 bearer token 向 new-api 核验身份，且只接受 `role === 100`。
- 后台持续监控使用单独的 Root Personal Access Token，只执行读取；未配置令牌时仍允许 Root 手动刷新。
- 管理员界面首版只提供简体中文，文案经独立 resolver 暴露后续 i18n 接口。
- new-api 是物理渠道、选路、测试和日志的事实来源；管理员服务是逻辑元数据的事实来源，写入 new-api 的 Partokens 元数据只是兼容镜像。

## 2. 已核实的 new-api 约束

### 2.1 路由字段属于物理渠道

new-api 的 `group`、`priority`、`weight` 均保存在物理渠道及其 ability 记录上，不能直接表达“同一个上游在不同分组中使用不同优先级和权重”。

- `priority` 数值越大越先使用。
- 第 0 次尝试使用最高优先级，第 1 次重试使用第二个不同优先级，之后依次下降。
- 同一优先级内按 `weight` 随机分配，不保证固定顺序。
- 当重试次数超过优先级层数时，会继续使用最低优先级层。
- 总尝试次数受全局 `RetryTimes + 1` 限制。

因此，同一逻辑渠道如果出现在多个分组、多个尝试层，使用现有接口时必须对应多条物理渠道记录。

**针对当前需求的可实现口径：** A、B 放在同一最高优先级时，new-api 会在 A/B 中按权重选一个；该请求失败后进入下一优先级 C。因此可以实现 `A -> C` 或 `B -> C`，不能保证 `A -> B -> C` 或 `B -> A -> C`。如果把 A、B、C 设置为三个不同优先级，则可以得到固定层级顺序，但无法同时满足 A/B 互为首选的随机入口。

### 2.2 渠道列表不返回密钥

常规渠道列表和详情会省略 `key`。完整密钥只能由 Root 账户在安全验证后读取。界面不能仅凭现有列表自动判断两条历史记录是否使用同一个密钥。

### 2.3 现有接口不是事务型批量配置接口

现有能力包括单条更新、复制渠道、批量启停、批量标签和按标签编辑，但没有“提交完整分组路由”的事务接口。一次产品操作可能需要多次请求，且中途失败时服务端不会整体回滚。

### 2.4 成本倍率不是现有计费字段

new-api 当前计费使用模型倍率、模型固定价格和用户分组倍率；没有独立的渠道成本倍率。本文中的“成本倍率”先定义为 Partokens 管理员元数据，不自动改变用户扣费。

### 2.5 可复用的监控数据有限

现有渠道字段可提供启停状态、自动禁用原因、最近测试时间、最近测试延迟、余额、余额更新时间和累计使用额度。管理员日志可按底层 `channel_id` 查询请求记录。

现有接口没有逻辑渠道级 SLA、渠道级历史测试序列、真实上游成本或一次性全渠道窗口聚合。24 小时成功率可以在错误日志和消费日志均启用时按物理渠道尝试聚合；任一日志类型缺失时显示“暂无数据”，不伪造百分比。

## 3. 核心对象

### 3.1 逻辑渠道

管理员认识和维护的上游账户，例如 A、B、C。身份定义为：

```text
渠道类型 + 规范化 API 地址 + API 密钥指纹
```

逻辑渠道包含：

- 显示名称
- 渠道类型
- 规范化 API 地址
- 不可逆密钥指纹，不保存或展示明文密钥
- 成本倍率
- 模型范围与映射
- 人工备注
- 当前健康摘要
- 对应的物理执行记录

API 地址规范化至少处理协议和主机大小写、默认地址、尾部斜杠；不应擅自合并不同路径。

### 3.2 凭据模板

每个逻辑渠道保留一条不参与用户路由的禁用物理渠道，作为复制来源：

- 分组固定为保留组，例如 `__partokens_catalog__`。
- 状态固定为手动禁用。
- 保存真实类型、地址、密钥、模型和上游配置。
- 日常生成执行记录时，由后端复制该记录，不把明文密钥传回浏览器。

这是基于现有 API 实现安全展开的推荐方式。首版不设计历史渠道接管；页面上线后由管理员使用新版本功能重建全部渠道。

### 3.3 执行记录

实际参与 new-api 选路的物理渠道。每条执行记录只承载一个目标分组和一个尝试层，包含由产品层生成的 `priority`、`weight` 和路由修订号。

建议自动命名：

```text
A · plus · 初次 · r7
A · plus · 重试1 · r7
```

默认不要求管理员理解或编辑物理 ID；展开逻辑渠道时可以查看，以便故障排查和回到官方管理页核对。

### 3.4 分组路由

一个现有用户分组的一套尝试策略。分组本身及其倍率在其他页面维护，本页面只维护该分组绑定的渠道和尝试层。每个尝试层是一个渠道池，而不是有序列表：

```text
plus
  初次尝试  A 60% / B 40%
  第1次重试 C 100%
```

如果业务要求严格的 `A -> B -> C` 或 `B -> A -> C` 顺序，现有权重路由不能保证；首版明确采用 `A/B -> C` 的两层候选池方案。

## 4. 元数据建议

推荐保留现有 provider `settings`，避免与 new-api 自有配置冲突。当前确认 `tag` 和 `remark` 均无其他用途，因此可直接作为 Partokens 管理元数据承载字段：

- `tag`：逻辑渠道稳定 ID，例如 `ptlc:01J...`，也可登记简短的管理标识。
- `remark`：保存管理员可读备注；如需 JSON，必须保留长度校验和版本字段。
- `other_info`：在独立命名空间保存 Partokens JSON，并与 `status_reason` 等 new-api 键合并，不覆盖未知键。

示意：

```json
{
  "partokens_admin": {
    "schema": 1,
    "logical_id": "lc_01J...",
    "kind": "template",
    "cost_ratio": 0.08,
    "credential_fingerprint": "sha256:...",
    "route_revision": 7
  }
}
```

执行记录把 `kind` 设为 `route`，并登记 `group`、`attempt` 和 `route_revision`。旧记录可标记为 `archive`，用于变更回退和日志关联。

首版不需要兼容历史标签语义；重建渠道时由本页面统一写入逻辑渠道标识。

### 5.1 渠道页

页面顶部只保留一个紧凑工具栏：搜索、状态、类型、成本倍率完整性、标准状态，以及“新增渠道”。

桌面表格：

| 列 | 内容 |
| --- | --- |
| 状态 | 可用、部分异常、不可用、已停用、待核对 |
| 渠道 | 名称、类型、逻辑 ID 短码 |
| API 地址 | 主机与必要路径，完整值在详情显示 |
| 成本倍率 | 例如 `0.08x`，未登记时明确标空 |
| 路由 | 覆盖分组数、尝试层数、底层记录数 |
| 最近测试 | 时间、延迟或未测试 |
| 当前流量 | 现有日志可证明时显示 24h 尝试数；否则显示“暂无数据” |
| 操作 | 编辑、测试、启停、更多 |

点击行打开详情抽屉，分为“概览、路由实例、监控、变更”四个页签。API 密钥默认只显示“已登记”和指纹短码；轮换密钥是单独的高风险流程。

“非标准记录”区域只展示不含完整 Partokens 元数据的物理渠道基本属性，不提供编辑、测试、启停或绑定操作。

#### 渠道模型运营增强

- 成本倍率接受非负数且最多三位小数，服务端以整数千分位保存，页面统一显示三位小数。
- 渠道详情通过 new-api `GET /api/channel/fetch_models/{id}` 获取模板渠道的上游模型；发现结果单独保存，不自动覆盖配置模型。
- Root 可选择最多 100 个模型启动后台测试。服务端最大并发为 4，单模型超时为 10 秒，仅网络连接或超时最多短重试一次；同一逻辑渠道只允许一个活动任务。
- 任务和逐模型结果保存在 SQLite，刷新或关闭浏览器后仍可读取。前端只显示中文脱敏状态、延迟和原因。
- “移除不可用模型”仅接受最近测试中明确为 `unavailable` 的模型。操作先预览模板、路由和归档镜像的 `models`/`model_mapping` 变化，再按现有非原子变更步骤执行并支持续跑。
- `timeout`、`rate_limited`、`server_error`、`unauthorized` 和 `unknown` 一律保留，不触发自动禁用。

### 5.2 分组路由页

左侧选择现有分组，右侧按尝试层编辑。尝试层是稳定的横向带，不画装饰性流程图：

```text
plus                                      系统允许 2 次重试
────────────────────────────────────────────────────────────
初次尝试       A  [60%]      B  [40%]              [+ 渠道]
第1次重试      C  [100%]                           [+ 渠道]
────────────────────────────────────────────────────────────
模型覆盖       18 个完整 / 2 个在回退层缺失             [查看]
非标准记录     0
                                             [预览变更] [保存]
```

交互规则：

- “添加重试”最多达到全局重试次数；超出时明确阻止保存。
- 一个逻辑渠道不得重复出现在同一分组的不同尝试层；渠道选择器隐藏已在其他尝试层使用的渠道，保存校验再次阻止重复。
- 同层权重使用数字输入和计算后的百分比，不用拖拽顺序暗示确定性。
- 原始 `priority` 默认隐藏在高级详情中，由系统按尝试层生成。
- 保存前必须展示模型覆盖差异和非标准物理渠道；这些记录可能继续参与实际选路结果。
- 当某渠道不支持某个模型时，该模型的实际回退链会缩短，模型覆盖视图必须准确显示。

### 5.3 监控页

监控页优先回答“现在是否能路由”和“哪里需要处理”，不先做通用图表仪表盘。

顶部数据带：

- 可用逻辑渠道数
- 部分异常数
- 自动禁用执行记录数
- 无完整回退的分组/模型数
- 最近一次同步时间

主体包含三种视图：

1. **问题队列**：自动禁用、模板缺失、执行记录漂移、版本不一致、测试过期、无模型覆盖、成本倍率缺失。
2. **渠道状态表**：逻辑渠道聚合状态，展开后显示每条执行记录的状态、测试时间、延迟和原因。
3. **路由就绪矩阵**：按分组和模型展示每次尝试是否至少有一个启用渠道。

首版健康口径：

- **可用**：配置一致，且每个已配置路由实例均启用；存在近期成功测试时一并显示。
- **部分异常**：至少一个实例可用，但存在自动禁用、配置漂移或测试异常。
- **不可用**：所有应参与路由的实例均不可用，或关键模型没有任何可用实例。
- **已停用**：管理员明确停用逻辑渠道。
- **未知**：没有足够的测试或状态数据。

状态必须同时展示数据时间。最近测试延迟只是测试快照，不命名为实时延迟或 SLA。

详情按需加载 24h 尝试数、成功率和额度统计。成功率确定为：`消费日志数 / (消费日志数 + 错误日志数)`，按底层物理渠道聚合后映射到逻辑渠道；它衡量渠道尝试成功，不等于用户请求最终成功率。若日志未启用，显示数据不可用。若未来需要更长窗口或全渠道持续聚合，应新增服务端聚合能力，不通过浏览器遍历全部日志模拟。

### 5.4 变更预览与记录

任何会修改多条物理数据的操作先进入预览抽屉：

```text
保存 plus 路由
  新建并配置执行记录     5
  启用新记录             5
  停用旧记录             4
  保留归档               4
  不受影响               7

路由影响
  初次尝试  A/B -> A/B
  重试1     无   -> C

风险
  非原子提交；切换期间可能短暂存在新旧记录并行
```

执行后显示每一步状态和底层 ID。失败时不只给 toast，而是保留一条“需要处理”的变更记录，提供“继续执行”“重新核对”“按旧修订恢复”。

## 6. 关键流程

### 6.1 新增逻辑渠道

1. 输入名称、类型、API 地址、API 密钥、成本倍率和模型范围。
2. 浏览器仅在内存中计算密钥指纹，用于检测同身份逻辑渠道；不写入日志或本地存储。
3. 先测试未保存配置。
4. 创建禁用凭据模板，不直接进入任何用户分组。
5. 引导管理员去分组路由中使用该渠道。

如果命中相同类型、地址和密钥指纹，默认阻止重复创建并打开现有逻辑渠道。产品唯一性约束为：渠道类型 + 规范化 API 地址 + API 密钥；不允许创建第二个相同身份的逻辑渠道。

### 6.2 不在首版处理历史渠道

上线前不读取、合并或迁移历史渠道。管理员在新页面上线后，按新的逻辑渠道模型重新创建全部渠道和分组绑定。

不符合新页面数据标准的历史渠道只展示基本属性，不提供编辑、测试、启停或绑定操作。

### 6.3 保存分组路由

在不新增后端事务接口的前提下，推荐采用修订式切换：

1. 重新读取所有相关记录，检查是否与预览快照一致。
2. 从禁用模板复制缺失记录；复制件保持禁用。
3. 在禁用状态下写入分组、优先级、权重、名称和路由修订。
4. 逐条读取核对新记录。
5. 批量启用新修订。
6. 批量停用旧修订。
7. 再次读取并验证实际路由；旧记录标记归档。

采用“先启用新修订，再停用旧修订”可以避免完全断路，但切换瞬间可能短暂增加候选记录。若不能接受，应增加服务端事务接口。

### 6.4 编辑或轮换密钥

普通名称、成本倍率和备注只修改逻辑渠道元数据。类型、地址、密钥、模型和 provider 设置变化时，不直接逐条覆盖在线记录：

1. 更新并测试禁用模板。
2. 从新模板生成一套新的路由修订。
3. 验证后切换。
4. 保留旧修订一段时间，允许无需读取旧密钥即可恢复。

## 7. 示例落地

假设“优先”表示同层渠道池，而不是确定顺序：

```text
渠道
A 0.08x   B 0.08x   C 0.10x   D 0.12x   E 0.16x

plus
初次尝试：A、B（同一优先级候选池）
第1次重试：C

pro
初次尝试：C
第1次重试：D
```

产品层会生成类似下表的执行记录：

| 逻辑渠道 | 分组 | 尝试层 | 生成优先级 | 权重 |
| --- | --- | ---: | ---: | ---: |
| A | plus | 0 | 1000 | 100 |
| B | plus | 0 | 1000 | 100 |
| C | plus | 1 | 900 | 100 |
| C | pro | 0 | 1000 | 100 |
| D | pro | 1 | 900 | 100 |

绝对优先级数字不作为产品概念，只要求同一分组内层级关系正确。目标分组存在非标准渠道时必须阻止或强警告保存，否则它们可能与生成记录共同参与实际选路。

## 8. 权限与安全

- 任何 `role !== 100` 的用户均不可访问管理员路由和相关数据。
- 仅 Root 可访问和操作本页面；角色 10 不提供降级操作集。
- 创建模板、复制渠道、改变地址或密钥需要 `ChannelSensitiveWrite`。
- 查看完整密钥不是日常工作流；新建或轮换时只在当前内存流程中使用，不写入前端状态持久层。
- 密钥不得进入 URL、日志、React Query 持久缓存、浏览器存储、错误上报或变更记录。
- 每次批量操作记录操作者、时间、逻辑对象、底层 ID、旧/新修订和结果；不记录密钥。
- 原生管理页的人工修改可能制造漂移。管理员台必须检测并展示，不静默覆盖。

## 9. 首版范围建议

### 首版已落地

- 独立管理员壳与权限守卫
- 逻辑渠道目录、详情和创建
- 成本倍率元数据
- 现有分组的尝试层/相对权重配置；首版策略为同层候选池失败后进入下一优先级

- 当前状态监控、问题队列、路由就绪矩阵和可用时的 24h 渠道尝试成功率

- 其他原生管理页跳转与物理 ID 核对

### 后续补齐

- 密钥、类型、地址和模型范围的修订式轮换
- 按分组与模型展开的完整路由就绪矩阵
- 旧修订的一键恢复与归档清理策略

### P1

## 10. 主要风险与产品护栏

| 风险 | 护栏 |
| --- | --- |
| 同一逻辑渠道在多个尝试层可能再次命中同一故障上游 | 产品规则禁止同一分组跨尝试层重复选择；选择和保存两处校验 |
| 自动禁用只作用于单条物理记录 | 显示“部分异常”；批量处置；不把单条成功等同于逻辑渠道完全健康 |
| 多 API 提交中断 | 禁用状态下预配置、修订式切换、步骤日志、续跑与读回核对 |
| 原生页面修改造成漂移 | 对比期望修订和实际字段，阻止盲目覆盖 |
| 模型集合不同导致实际链路不同 | 保存前模型覆盖矩阵；不能只展示分组级抽象链路 |
| `other_info` 与 new-api 状态字段共存 | 命名空间、读取后合并、保留未知键 |
| 不符合新页面标准的历史渠道 | 只读展示基本属性，不提供操作 |

## 11. 最终补充决策

- 24 小时成功率采用渠道尝试口径：`消费日志数 / (消费日志数 + 错误日志数)`。日志条件不满足时显示“暂无数据”，不补算。
- 同一逻辑渠道禁止在同一分组的多个尝试层重复出现。
- 相对权重暂按非负整数录入并展示归一化百分比；具体输入上限在原型评审时按控件手感确定，不影响数据语义。
- 模型范围继续由渠道自身模型集合决定。当前页面统一配置分组绑定，模型覆盖矩阵只做校验和监控，不产生第二套路由配置。
- 本轮产品设计不存在阻塞性疑问，可以进入低保真交互原型阶段。
